# Спецификация soldout: друзья рядом (V3)

Версия: HW1, 2026-10-26. Владелец: akolenko. Статус: принята.

## 1. Легенда и контекст

Компания друзей покупает от одного до четырёх билетов. Покупателю нужен непрерывный
отрезок в одном ряду выбранного сектора. Четыре независимых hold оставляют пользователя
с частью мест при конфликте. Поэтому поиск и создание всей группы — одна транзакция.
Среди свободных отрезков предпочитаем меньший номер ряда, затем места: первый ряд
становится горячим. Истина о занятости остаётся в booking, карта зала может отставать.

## 2. Роли

| Роль | Что делает |
|---|---|
| Покупатель | получает admission, запрашивает группу, создаёт заказ, платит, получает N билетов |
| Оператор | запускает нагрузку и проверяет инварианты и доставку событий |
| Администратор | задаёт неизменяемую геометрию зала до начала продаж |

## 3. Функциональные требования

| ID | Требование | В этой версии |
|---|---|---|
| FR-G1 | POST /v1/holds/group: event_id, sector_id, user_id, size ∈ [1,4], admission и Idempotency-Key | да |
| FR-G2 | N различных свободных мест одного seated-сектора, один положительный row_no, последовательные seat_no | да |
| FR-G3 | Успех создаёт ровно N hold с единым временем истечения через 10 минут; конфликт не создаёт ни группы, ни hold, ни бизнес-события | да |
| FR-G4 | Пересекающиеся групповые и одиночные запросы не удерживают одно место дважды | да |
| FR-G5 | active + confirmed hold пользователя на мероприятии ≤ 4, включая смешанные конкурентные запросы | да |
| FR-G6 | Повтор ключа и тех же параметров возвращает ту же группу без продления TTL; другие параметры → 409 | да |
| FR-G7 | Группа проходит существующий order → pay → tickets, сумма N × TICKET_PRICE_MINOR | да |
| FR-G8 | GroupHeld записывается через outbox в транзакции создания; повтор ключа не порождает нового события | да |
| FR-G9 | Чужая площадка / standing / размер вне диапазона → 422, нет мероприятия/сектора → 404, нет непрерывного блока → 409 | да |

Атомарность FR-G3 относится к созданию группы. Далее действуют обычные операции
над hold: можно освободить отдельное место или заказать часть группы. Исторический
состав группы сохраняется. Строгая гарантия «самый первый свободный ряд» при конкуренции
не требуется: можно пропустить блок, который сейчас заблокирован другим запросом.

## 5. Расчёт нагрузки

Допущения, а не измерения: из 120 000 заинтересованных за сутки 30% приходят в первые
10 минут: 120 000 × 0.30 / 600 = 60 групп/с. Размеры 1/2/3/4 распределены как
10/40/30/20%: E[N] = 0.1 + 0.8 + 0.9 + 0.8 = 2.6 места. Группа делает join,
group hold, order, pay, tickets: 5 запросов → 300 HTTP RPS; запись hold — 156 строк/с.
В среднем за сутки 120 000 / 86 400 = 1.39 групп/с; коэффициент пика 43.2.
При среднем времени полного потока 0.5 с закон Литтла даёт 60 × 0.5 = 30
одновременно выполняемых потоков, без учёта пользовательского размышления.

Лабораторный поток — 20 групп/с, 100 HTTP RPS, 52 hold/с. За 60 с запрашивается
3120 мест; это меньше 78 000 seated-мест второго мероприятия. 80% запросов выбирают
первые четыре сектора, 20% — остальные 74: проверяем горячую область и длинный поиск
в постепенно заполненных рядах. Отказы 409 допустимы только при отсутствии блока,
но положительный счётчик завершённых покупок обязателен, чтобы пустой тест не прошёл.

Группа в JSON до 2 КБ × 60 = 120 КБ/с, остальные 4 ответа суммарно до 4 КБ
→ ещё 240 КБ/с, всего до 360 КБ/с без заголовков. Для 30 000 групп метаданные
~300 Б × 30 000 = 9 МБ; 78 000 позиций × ~120 Б ≈ 9.4 МБ без индексов.
Рычаги: admission ограничивает вход, размер группы ограничен четырьмя, SQL-поиск
должен зависеть от сектора (1000 мест), а не всего мероприятия.

## 6. Ограничения

Go 1.27, PostgreSQL 17, существующие зависимости и границы модулей. Отправная точка
только lesson-5, собственная реализация трека А. Известные I3/I6 исходного кода
рассматриваются отдельно от вариации. Не изменяем старые миграции. Обязательный
EVENTBUS_BUFFER=40000 в compose/lesson-04.yml. Все прогоны сравниваются после
одинаковой очистки данных, ANALYZE, с одинаковыми seed, интенсивностью и лимитами.

## 7. Модули и владение данными

| Модуль | Ответственность | Данные |
|---|---|---|
| catalog | проверка seated-сектора, геометрия мест через публичный SectorLayout | seats/sectors/events |
| booking | выбор блока, блокировки, лимит, идемпотентность, group hold | holds, hold_groups, hold_group_items, orders |
| platform/outbox | надёжная публикация GroupHeld в транзакции booking | outbox |
| payment/ticketing/notification | прежний полный путь покупки | без новых таблиц |

Зависимости закреплены .go-arch-lint.yml. booking не читает seats/sectors SQL-запросами.
hold_groups(id,event_id,sector_id,user_id,size,row_no,first_seat_no,idempotency_key,
created_at,expires_at), hold_group_items(group_id,hold_id,seat_id,row_no,seat_no).
FK только внутри booking. Схема расширяется новыми таблицами, старый бинарник работает.

## 8. Инварианты

I1–I6 сохраняются из основной спецификации. Новый **I7**: каждая сохранённая группа
содержит ровно size hold, одного event/user/TTL, с местами выбранного сектора и ряда,
без пропусков от first_seat_no до first_seat_no+size−1. Проверяется checker по истинной
геометрии catalog, включая исторические released/confirmed hold. **I8**: количество
active+confirmed hold пользователя на событие не больше 4. Идемпотентность защищена
UNIQUE ключом и транзакционной блокировкой; проверяется также конкурентным тестом.

## 9. API и события

Контракт api/openapi.yaml. join → POST /v1/holds/group → POST /v1/orders с hold_ids
группы → pay → tickets. Первый group запрос: 201, повтор: 200. GroupHeld:
spec/events/group-held.yaml, aggregate=group, отдельный outbox.event.group. Потребитель
в HW1 не требуется. Имеющийся OrderPaid остаётся в outbox; события карты — прежняя
асинхронная проекция с известными ограничениями lesson-5.

## 10. Не в scope

Совместная оплата несколькими пользователями, соседние ряды, группы >4, standing,
изменение геометрии во время продаж, групповая сага и исправление I3 исходного pay.
