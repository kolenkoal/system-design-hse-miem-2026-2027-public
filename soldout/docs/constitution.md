# Конституция проекта `soldout`

Неизменяемые принципы. Любое отклонение оформляется ADR в `docs/adr/`, а не кодом. Агент и человек обязаны соблюдать их одинаково.

## 1. Назначение

`soldout` — система продажи билетов на «дроп»: один концерт, 40 000 мест, порядка 2 000 000 желающих, старт продаж в 12:00. Главные свойства: **ноль двойных продаж**, ноль потерянных оплаченных заказов, предсказуемая латентность под штормом. Спецификация — `spec/soldout.md`, контракт API — `api/openapi.yaml`.

## 2. Архитектурный стиль

Модульный монолит (ADR-001). Модули: `catalog`, `queue`, `booking`, `payment`, `ticketing`, `notification`, технический `platform`. Каждый модуль — каталог `internal/<module>/` с пакетами `api` (публичный контракт: DTO, ошибки, интерфейсы), `domain` (сущности и правила, без I/O), `app` (сценарии), `adapters/*` (HTTP, PostgreSQL, Valkey, эмуляторы).

Правило зависимостей (проверяется `make lint-arch`, файл `.go-arch-lint.yml`):

- модуль импортирует другой модуль **только через его пакет `api`**, никогда `domain`/`app`/`adapters`;
- разрешённые рёбра: `booking → catalog.api, queue.api`; `payment → booking.api`; `ticketing → booking.api`; `notification → booking.api` (событие `OrderPaidEvent`, занятие 4); `queue → catalog.api`; `catalog → booking.api` (статусы мест, `sold_count`);
- `platform` не зависит ни от одного бизнес-модуля; `cmd` собирает всё;
- модуль **владеет своими таблицами**; чужие таблицы — только через `api` владельца, никаких JOIN'ов между модулями в SQL;
- обратные вызовы (booking → payment/ticketing) — через порты, объявленные в `booking/api`, реализации подставляет `cmd`.

## 3. Инварианты домена

Нарушение инварианта важнее любой фичи. Проверяются `tools/invariant-checker` (`make invariants`) после каждого нагрузочного прогона.

- **I1.** На одно `(event, seat)` — не более одного `active` hold (в БД: `uniq_active_hold`).
- **I2.** На одно `(event, seat)` — не более одного билета.
- **I3.** У каждого `paid` заказа есть билет на каждую позицию.
- **I4.** У пользователя не более 4 билетов на мероприятие (FR-7).
- **I5.** Каждому `paid` заказу соответствует ровно одно уведомление (`notifications`, kind `tickets_issued`). Проверяется по умолчанию с занятия 4.

## 4. Правила кода

- Go 1.27, стандартная библиотека прежде фреймворков; из внешнего — только то, что уже в `go.mod` (`chi`, `pgx`, `valkey-go`, `prometheus`, `golang-migrate`, `uuid`; с занятия 4 по ADR-003 OpenTelemetry, `otelpgx`, `franz-go`).
- `context.Context` и таймаут на каждый I/O; фоновые циклы завершаются по `ctx.Done()`.
- Ошибки оборачиваются (`fmt.Errorf("...: %w", err)`); доменные ошибки — sentinel-значения в `api`, HTTP-коды назначает только `adapters/http`.
- Никаких глобальных переменных состояния: зависимости передаются через конструкторы в `cmd/soldout/main.go`.
- Идемпотентность для всех мутирующих операций с внешним эффектом: заказ — по `Idempotency-Key`, платёж — по ключу в `payments`, выпуск билета — по `(order_id, seat_id)`.
- Событие, потеря которого нарушает инвариант или обязательство перед пользователем, публикуется только через outbox в транзакции издателя (`platform/outbox`, ADR-003); после commit допустимы только вызовы, потерю которых система переживает. Проверяется semgrep `no-network-after-commit` (`make lint-semgrep`).
- Потребитель события идемпотентен по id события: доставка at-least-once, повтор не создает второго эффекта.
- Конкурентный доступ к месту сериализуется в транзакции (advisory-lock), уникальность закрепляется индексом; «проверил — потом записал» без блокировки запрещено.

## 5. Данные

- Схема меняется только новым файлом в `migrations/` (`NNNN_name.up.sql` + `.down.sql`); существующие миграции не редактируются.
- Никаких `SELECT *`; каждый запрос начинается с комментария `/* module.name */` (метрика `db_query_duration_seconds`).
- Каждая новая таблица — с `COMMENT` (владелец-модуль) и индексами под известные запросы; отсутствие индекса — только осознанно и через ADR (см. «известные ограничения» ADR-001).
- FK между таблицами разных модулей не заводятся (модуль может уехать в отдельную БД).

## 6. Наблюдаемость

Каждый HTTP-хендлер: RED-метрики (`http_requests_total`, `http_request_duration_seconds` с `method/route/status`) и структурный лог с `request_id`. Обязательны `/healthz`, `/readyz`, `/metrics`, `/debug/pprof`. Ошибки логируются один раз, там, где обрабатываются.

Каждый входящий запрос и каждое потребленное сообщение имеют trace_id; логи несут trace_id (OpenTelemetry, `platform/otel`, контекст W3C `traceparent` едет через HTTP и заголовки Kafka). Каждый внешний вызов обернут в span. Что где смотреть: `docs/observability.md`.

## 7. Тесты

Каждая доменная операция покрыта unit-тестом в `domain`; каждая конкурентная операция — интеграционным тестом (testcontainers, PostgreSQL 17); `go test ./...` укладывается в 60 с.

## 8. Процесс

Перед завершением любой задачи: `make lint-arch && make test && make invariants` (последнее — на поднятом стенде) зелёные. Отклонение от конституции — только через ADR по шаблону `templates/adr.md`.
