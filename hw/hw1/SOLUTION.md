## Что реализовано

`POST /v1/holds/group` получает event_id, sector_id, user_id, size (1–4),
`X-Admission-Token` и `Idempotency-Key`. Ответ 201 содержит N hold одного ряда с
последовательными номерами мест и общим TTL. Повтор возвращает ту же группу с кодом
200 без нового события или продления TTL, другой набор параметров — 409.
При отсутствии блока — 409, при ошибке транзакции не остаётся частичной группы.

| Область | Файлы и поведение |
|---|---|
| Контракт | [OpenAPI](../../soldout/api/openapi.yaml), DTO в booking/api |
| Геометрия | [catalog/app/group.go](../../soldout/internal/catalog/app/group.go), публичный GroupLayout: seated-сектор своей площадки |
| Правила | [domain/group.go](../../soldout/internal/booking/domain/group.go): непрерывные окна по row_no/seat_no, а не seat_id |
| Сценарий | [app/group.go](../../soldout/internal/booking/app/group.go): одна транзакция, ключ → user → sector → места по id |
| Хранилище | [pg/group.go](../../soldout/internal/booking/adapters/pg/group.go): истина из holds, пакетные запросы, outbox |
| Схема | Только новые [0023 up](../../soldout/migrations/0023_hold_groups.up.sql) и [down](../../soldout/migrations/0023_hold_groups.down.sql): hold_groups, hold_group_items |
| Событие | [GroupHeld](../../soldout/spec/events/group-held.yaml), aggregate=group, outbox.event.group; OrderPaid сохранён |
| Проверки | [I7/I8](../../soldout/tools/invariant-checker/main.go), unit и PostgreSQL integration tests |
| Нагрузка | [k6/friends.js](../../soldout/k6/friends.js), `make friends`, [measure.py](../../soldout/tools/hw1/measure.py) |

booking не читает таблицы catalog. В новой схеме нет FK через границы модулей.
Старые миграции и constitution не изменялись. Одиночный CreateHold также берёт
блокировку `(event,user)`: иначе single/group вместе обходили бы лимит четырёх.
События карты зала остаются прежней проекцией после commit, а обязательство GroupHeld
сохраняется в outbox вместе с группой. Потребитель нового события — вне HW1.

**I7:** исторический состав каждой группы — ровно size hold одного event/user/TTL,
истинные места одного seated-сектора/ряда образуют отрезок. **I8:** active+confirmed
hold пользователя на мероприятии ≤4. Проверяется и подтверждённая, и освобождённая
история; release отдельного hold не удаляет состав группы.

## Проверка корректности

Конкурентные тесты выполняются с PostgreSQL 17 через testcontainers, общий старт
горутин — каналом, без ожиданий для синхронизации. Проверены размеры 1–4, разрывы,
границы рядов, standing и чужая площадка; один победитель на единственный блок;
параллельные группы и single; смешанный лимит одного пользователя; параллельный
повтор ключа; rollback при отказе outbox; order/pay и истечение TTL.
Интеграционный тест использует заглушку ticket issuer; реальная выдача N билетов
проверяется отдельно сценарием k6 через HTTP. Это разные уровни проверки.

### Оптимизация 1: убрать последовательные проверки занятости

Симптом: group p99 39.55 мс при низкой загрузке CPU. В
[pg_stat_statements baseline](artifacts/baseline/pg-statements.json)
`group_seat_taken` вызван 48 825 раз (313.24 мс серверного времени).
[Трейс](artifacts/baseline/slow-trace.json) содержит 102 проверки на один запрос:
23.48 мс внутри HTTP-запроса 48.61 мс. Это два независимых источника.

[EXPLAIN](artifacts/baseline/explain.txt) уже показывает Index Only Scan по
holds_taken_uidx, Execution Time 0.054 мс. Узкое место — число последовательных
round trip, новый индекс здесь не решает проблему. В [CPU-профиле](artifacts/baseline/pprof.txt)
за 20 с собрано 1.48 с CPU, лидируют syscall/futex. Профиль CPU не измеряет ожидание
сети и не доказывает насыщение PostgreSQL.

Исправление a03f036: одна выборка занятых мест заданного сектора, фильтрация окон
в памяти, затем блокировка выбранных мест и повторная пакетная проверка истины.
Занятость не кэшируется. Запросов проверки стало **962 вместо 48 825 (−98.03%)**,
их серверное время **43.83 вместо 313.24 мс (−86.01%)**.
Group p99 **39.55 → 10.11 мс (−74.43%)**, p50 **13.44 → 4.93 мс**.

### Оптимизация 2: пакетная запись группы

После первой оптимизации остаются отдельные INSERT hold и позиции. В
[SQL-статистике opt1](artifacts/opt1/pg-statements.json) это 1249 + 1249 вызовов,
71.15 + 65.45 мс серверного времени, дополнительно — один INSERT метаданных на группу.
[Трейс opt1](artifacts/opt1/slow-trace.json) для size=4 содержит девять INSERT
метаданных/hold/позиций: суммарно 2.69 мс. Это второй независимый источник.

Исправление 8e8d403: один SQL с CTE и unnest создаёт hold_groups, N holds и N items.
FK/UNIQUE и запись outbox в той же транзакции сохранены. Теперь
[insert_group_bulk](artifacts/opt2/pg-statements.json) вызван **481 раз**, серверное
время **139.21 мс** за все три сущности. Количество запросов записи уменьшено
с 481 + 2×1249 = 2979 до 481 (**−83.85%**). В
[трейсе opt2](artifacts/opt2/slow-trace.json) для size=4 запись занимает один span
0.87 мс. Разные отдельные трейсы иллюстрируют состав времени; основной эффект
подтверждается всей выборкой k6, а не сравнением двух единичных запросов.

Group p99 **10.11 → 8.63 мс (−14.66%)**, p50 **4.93 → 4.57 мс**.
Суммарно относительно baseline: p99 **−78.18%**. Серверный INSERT не стал в разы
дешевле: выигрыш даёт сокращение последовательных сетевых обменов.

Один диагностический прогон на ступень, 481 покупка: доверительные интервалы не
оценивались. Результат относится к этим данным и ресурсам, а не к production SLO.
Tempo использует штатное семплирование шумных маршрутов 10%: сохранён самый медленный
из найденных трейсов периода, он не обязательно совпадает с абсолютным max k6.

### Что не оптимизировали

Не кэшируем занятость: асинхронная карта может отставать, и это угрожает корректности.
Не добавляем ещё один индекс на holds: существующий план уже индексный, подтверждено
EXPLAIN. Не снимаем сериализацию групп сектора и не вводим SKIP LOCKED/шардирование:
после двух изменений целевой бюджет выдержан, а новая схема усложнила бы выбор,
повторы и порядок блокировок. Главный вклад в полном checkout — эмулятор PSP около
300 мс; уменьшать его задержку ради цифры нельзя — это изменит условия эксперимента.

## Известные ограничения lesson-5

Обязательное `EVENTBUS_BUFFER: ${EVENTBUS_BUFFER:-40000}` добавлено в
compose/lesson-04.yml. Это исправление отправной точки не считается оптимизацией V3.
Инварианты запускаются после eventbus_queue_depth=0 и появления уведомлений.
I3 (билеты после commit pay) и риск потери событий проекции при исчерпании пула
сохранены, в прогонах V3 не воспроизвелись.

В штатном шторме http_req_failed: baseline: 20/598160 (0.00334%), opt1: 1/589866 (0.00017%), opt2: 0/574083 (0.00000%). Первые два прогона содержали HTTP 500 (подтверждено сохранёнными /metrics). Причина этих редких ошибок не установлена, журналы первых контейнеров не сохранены; не приписываем их известным I3/I6 без доказательств. Поэтому хвосты первых контрольных storm приведены только для полноты, вывод об эффекте оптимизаций делается по friends с нулевыми 5xx. Финальный storm прошёл без HTTP-ошибок, журналы ERROR/WARN пустые; I1–I8 соблюдены после каждого storm. Пороги штатного storm выполнены на всех трёх ступенях, но это не доказательство production SLO.

## Воспроизведение

Из каталога soldout, Docker должен работать. На Colima для testcontainers:

```bash
export DOCKER_HOST="unix://${HOME}/.colima/default/docker.sock"
export TESTCONTAINERS_DOCKER_SOCKET_OVERRIDE=/var/run/docker.sock
export TESTCONTAINERS_HOST_OVERRIDE=localhost
make lint-all
make test
make up
make friends
# Дождаться eventbus_queue_depth=0 в /metrics и доставки уведомлений (notifier lag=0).
make invariants
```

Полный сбор артефактов на отдельном учебном стенде:

```bash
# ВНИМАНИЕ: measure.py очищает данные покупок/проекции этого compose-стенда.
python3 tools/hw1/measure.py my-run --rate 20 --duration 60s --storm
python3 tools/hw1/summarize.py
```

Для воспроизведения таблицы последовательно взять d26e33a, a03f036, 8e8d403,
пересобрать soldout и запустить friends.js с одинаковыми 8 группами/с × 60 с.
У каждой ступени сохранены исходные k6 JSON, top SQL, EXPLAIN, CPU-профиль, трейс,
снимок метрик, ресурсные лимиты и результат инвариантов.

## Как использовался ИИ

Codex прочитал задание из main, взял код lesson-5, подготовил спецификацию/ADR,
реализацию, тесты и сценарий; запускал стенд, измерял, разбирал SQL и трейсы,
сделал две оптимизации и этот отчёт. Человек выбрал V3/full, текущую папку и
подтвердил план. Ручную реализацию или независимую проверку человеком не заявляем.

Ошибки агента и проверка:

1. Первый запуск Dockerfile упёрся в отсутствие Buildx. Установлен Buildx, после
   повторной сборки и /readyz подтверждён работающий стенд.
2. Первый testcontainers запуск не нашёл Docker Colima. Заданы DOCKER_HOST и override
   сокета; затем make test действительно исполнил интеграционные тесты с PostgreSQL.
3. Агент сначала сохранил stdout make pprof-top, где только сообщения ожидания:
   Makefile пишет сам профиль через tee в k6/results. Сборщик исправлен, baseline
   профиль скопирован из созданного во время нагрузки файла; непустой профиль проверяется.
4. Не подменяли исходные измерения готовой веткой трека Б, не снижали PSP_DELAY_MS
   и не выдавали требования к production RTO за проведённые испытания.
